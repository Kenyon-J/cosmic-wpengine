## 2025-02-27 - Unbounded Memory Growth via `.text().await`
**Vulnerability:** Similar to `.bytes().await` and `.json().await`, using `reqwest`'s `.text().await` buffers the entire response body into memory without a size limit. When fetching text files from untrusted sources (or potentially compromised sources, like an update server), a maliciously large response can cause an Out-Of-Memory (OOM) denial-of-service condition.
**Learning:** All `reqwest` response extraction methods that buffer the full payload (`bytes()`, `text()`, `json()`) are inherently vulnerable to OOM attacks if unbounded. The existing `read_capped` utility must be used uniformly across the codebase for all payloads—not just binary or JSON data—before converting to the desired format (e.g., parsing JSON or creating a String from UTF-8 bytes).
**Prevention:** Always read untrusted HTTP responses chunk-by-chunk with a strict, explicitly declared maximum size limit (e.g., using a helper function like `read_capped`) instead of relying on `reqwest`'s convenient buffering methods. Once the bounded byte buffer is safely retrieved, perform any necessary conversion (like `String::from_utf8(bytes)`) locally.

## 2025-02-27 - SSRF Vulnerability in User-Configured Proxy URLs
**Vulnerability:** A Server-Side Request Forgery (SSRF) vulnerability existed in `fetch_spotify_canvas` where user-configured proxy URLs (`audio.canvas_proxy_url`) were queried without checking if the resolved IP address was safe. An attacker could configure a malicious local URL (e.g., `http://127.0.0.1/admin`) and force the backend to make requests to internal services, potentially bypassing firewalls.
**Learning:** Even if a URL is provided by a seemingly "trusted" user configuration rather than external metadata, it must be verified before the application makes an HTTP request to it.
**Prevention:** Always validate that URLs fetched by the application resolve to safe, non-private IP addresses using `crate::modules::utils::is_safe_ip`. Apply the check manually using `tokio::net::lookup_host` when reusing a connection-pooled `reqwest::Client`.
## 2025-02-27 - Command Injection / Path Traversal Risk with xdg-open
**Vulnerability:** Untrusted or dynamically parsed URLs from Markdown (like patch notes) were being passed directly to `xdg-open` via `std::process::Command` without scheme validation. An attacker could embed a URL with a local or dangerous scheme (e.g., `file://`, `ssh://`, or custom URI handlers) into the markdown, which would then be executed by the desktop environment, potentially reading sensitive files or running arbitrary commands.
**Learning:** Even if a URL comes from a markdown parser that ostensibly creates a `Uri` object, it must still be validated against an explicit allowlist of safe schemes (like `http` and `https`) before being handed off to a generic system execution handler like `xdg-open`.
**Prevention:** Always parse untrusted URIs (e.g., using the `url` crate) and explicitly verify the scheme is `http` or `https` before passing the string to `xdg-open`.
## 2025-02-27 - Silently Ignored Process Spawns
**Vulnerability:** When launching external applications or opening files/URLs via `std::process::Command::new(...).spawn()`, errors were being silently discarded with `let _ = ...`. While not immediately exploitable for arbitrary code execution in this specific context (since the binaries being spawned like `xdg-open` were hardcoded or resolved from trusted paths), silently failing to launch a process degrades auditability and hides failures from users or logs.
**Learning:** Even low-risk process spawns should handle errors. System-level failures (like out-of-memory, file handle exhaustion, or missing executables) must be logged rather than suppressed.
**Prevention:** Always check the `Result` of `Command::spawn()`, even if just to log the error. Replace `let _ = Command::new(...).spawn();` with `if let Err(e) = Command::new(...).spawn() { tracing::error!("...", e); }`.
## 2025-02-27 - Silently Ignored Process Spawns
**Vulnerability:** System commands executed via `std::process::Command` (like `busctl` or `xdg-open`) were having their results explicitly ignored using `let _ = ...`. While not immediately exploitable for arbitrary code execution in these specific contexts, this practice degrades auditability and hides system-level failures (like missing executables or out-of-memory errors) from users and logs.
**Learning:** Even low-risk process spawns or executions should handle errors. System-level failures must be logged rather than suppressed to ensure issues can be debugged and audited.
**Prevention:** Always check the `Result` of `Command::spawn()` or `Command::output()`, even if just to log the error. Replace patterns like `let _ = Command::new(...).output();` with `if let Err(e) = Command::new(...).output() { tracing::error!("...", e); }`.
