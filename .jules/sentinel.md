## 2025-02-27 - Unbounded Memory Growth via `.text().await`
**Vulnerability:** Similar to `.bytes().await` and `.json().await`, using `reqwest`'s `.text().await` buffers the entire response body into memory without a size limit. When fetching text files from untrusted sources (or potentially compromised sources, like an update server), a maliciously large response can cause an Out-Of-Memory (OOM) denial-of-service condition.
**Learning:** All `reqwest` response extraction methods that buffer the full payload (`bytes()`, `text()`, `json()`) are inherently vulnerable to OOM attacks if unbounded. The existing `read_capped` utility must be used uniformly across the codebase for all payloads—not just binary or JSON data—before converting to the desired format (e.g., parsing JSON or creating a String from UTF-8 bytes).
**Prevention:** Always read untrusted HTTP responses chunk-by-chunk with a strict, explicitly declared maximum size limit (e.g., using a helper function like `read_capped`) instead of relying on `reqwest`'s convenient buffering methods. Once the bounded byte buffer is safely retrieved, perform any necessary conversion (like `String::from_utf8(bytes)`) locally.

## 2025-02-27 - SSRF Vulnerability in User-Configured Proxy URLs
**Vulnerability:** A Server-Side Request Forgery (SSRF) vulnerability existed in `fetch_spotify_canvas` where user-configured proxy URLs (`audio.canvas_proxy_url`) were queried without checking if the resolved IP address was safe. An attacker could configure a malicious local URL (e.g., `http://127.0.0.1/admin`) and force the backend to make requests to internal services, potentially bypassing firewalls.
**Learning:** Even if a URL is provided by a seemingly "trusted" user configuration rather than external metadata, it must be verified before the application makes an HTTP request to it.
**Prevention:** Always validate that URLs fetched by the application resolve to safe, non-private IP addresses using `crate::modules::utils::is_safe_ip`. Apply the check manually using `tokio::net::lookup_host` when reusing a connection-pooled `reqwest::Client`.

## 2025-02-27 - Command Injection / Malicious Protocols via Unvalidated `xdg-open`
**Vulnerability:** The application was passing a user-supplied (or external markdown-supplied) URL directly to `xdg-open` via `std::process::Command::new(xdg_open).arg(url).spawn()` in `on_patch_notes_link_clicked`. Passing unvalidated URLs to `xdg-open` is highly dangerous because attackers can embed malicious protocols (like `file://` to open arbitrary local files, or application-specific custom handlers) or even inject command-line flags.
**Learning:** External links parsed from Markdown (even from seemingly "trusted" sources like release notes) should never be blindly trusted and executed. Desktop environment launchers are complex and have historically been vulnerable to argument injection or unsafe protocol handling.
**Prevention:** When passing URLs to external viewers like `xdg-open`, always parse them using a robust parser (e.g., the `url` crate) and explicitly validate that their scheme is within a safe allowlist (typically only `http` and `https`). Pass the reconstructed, validated URL string to the command to prevent malformed injections.
